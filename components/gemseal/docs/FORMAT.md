# GEMSEAL format version 1

This document defines the bytes produced and accepted by `gemseal.py`. The format is experimental and has not received an independent cryptographic review.

## Conventions

- Integers are unsigned and little-endian unless stated otherwise.
- `||` means byte-string concatenation.
- `LE32(i)` is the four-byte little-endian encoding of `i`.
- `TAG` is the 16-byte Poly1305 authentication tag produced with ChaCha20-Poly1305.
- All multi-byte fields have fixed positions; native C structure layout is never used.

The explicit encoding avoids host-dependent Intel/Motorola byte order and alignment. It does not imply compatibility with any native GEM file format.

## Cryptographic suite

Version 1, suite 1, KDF 1 means:

- Master key: exactly 32 bytes, generated by a cryptographic random-number generator.
- File-key derivation: HKDF-SHA256 with a 32-byte output.
- Record encryption: ChaCha20-Poly1305 with a 12-byte nonce and 16-byte tag.

```text
file_key = HKDF-SHA256(
    ikm  = master_key,
    salt = file_salt,
    info = ASCII("GEMSEAL1/file-key\0"),
    L    = 32
)
```

HKDF is not a password-stretching function. A predictable master key remains predictable.

## File header

Every file begins with this 48-byte header:

| Offset | Size | Field | Version 1 value |
|---:|---:|---|---|
| 0 | 8 | Magic | ASCII `GEMSEAL1` |
| 8 | 2 | Format version | 1 |
| 10 | 2 | Cipher suite | 1 |
| 12 | 2 | KDF identifier | 1 |
| 14 | 2 | Header size | 48 |
| 16 | 16 | File salt | Random bytes |
| 32 | 8 | Nonce prefix | Random bytes |
| 40 | 4 | Maximum plaintext chunk size | 1 through 65519; default 4096 |
| 44 | 4 | Reserved | Zero |

The salt and nonce prefix are public parameters, not secrets. A fresh encryption generates both with the operating system CSPRNG.

## Record header

The file header is followed by records. Every record starts with a 16-byte header:

| Offset | Size | Field | Meaning |
|---:|---:|---|---|
| 0 | 2 | Record type | 1 = DATA, 2 = END |
| 2 | 2 | Cipher suite | Must equal the file-header suite |
| 4 | 2 | Sealed-body length | Plaintext length + 16 |
| 6 | 4 | Record index | Zero-based, consecutive |
| 10 | 4 | Plaintext length | DATA: 1 through chunk size; END: zero |
| 14 | 2 | Flags | Zero in version 1 |

The sealed body immediately follows the record header:

```text
sealed_body = ChaCha20-Poly1305-Encrypt(
    key        = file_key,
    nonce      = nonce_prefix || LE32(record_index),
    plaintext  = record_plaintext,
    aad        = record_aad
)

record_aad = ASCII("GEMSEAL1/record\0")
          || file_header
          || previous_tag
          || record_header
```

The AAD is 96 bytes: a 16-byte context string, 48-byte file header, 16-byte previous tag, and 16-byte record header.

`previous_tag` is sixteen zero bytes for record zero. After each DATA record, it becomes that record's final 16 bytes (its tag). The END record uses the last DATA tag, or sixteen zero bytes for an empty file.

The nonce is unique for every record under one file key:

```text
nonce = nonce_prefix || LE32(record_index)
        <--- 8 bytes --->    <- 4 bytes ->
```

## Record sequence

```text
file_header
DATA(index=0) || ciphertext_0 || tag_0
DATA(index=1) || ciphertext_1 || tag_1
...
END(index=D)  || empty_ciphertext || tag_D
```

`D` is the number of DATA records. Rules:

1. DATA records contain between 1 and the file-header chunk size of plaintext.
2. DATA indices run consecutively from zero through `D - 1`.
3. The encoder emits full chunks except possibly for the final DATA chunk.
4. There is exactly one END record and it has an empty plaintext body.
5. The END index is `D`; its sealed body is exactly one 16-byte tag.
6. There can be at most `2^32 - 1` DATA records, leaving the final index representable as `LE32(D)`.
7. Empty plaintext is represented by an END record only.
8. No bytes are permitted after the END record.

A decoder accepts authenticated short DATA records even when they are not the last DATA record. Such files are noncanonical but do not create an authentication bypass. New encoders must follow rule 3.

Ciphertext length equals plaintext length. Overhead is `80 + 32D` bytes: a 48-byte file header, 32 bytes per DATA header/tag pair, and a 32-byte END header/tag pair.

## Decryption requirements

Before publishing output, a decoder must:

1. Read exactly 48 bytes and validate every file-header field.
2. Reject unsupported versions, suites, KDFs, nonzero reserved fields, and invalid chunk sizes.
3. Derive the file key using the exact context string above.
4. Require consecutive indices and valid record types, lengths, and flags.
5. Reconstruct the previous-tag AAD chain and verify each record with ChaCha20-Poly1305.
6. Reject empty DATA records, oversized records, missing records, and truncated bodies.
7. Require an authenticated END record and reject trailing bytes.
8. On any failure, avoid publishing decrypted output.

The reference implementation writes to a temporary file, flushes and `fsync`s it, and uses a hard link to publish atomically without replacing an existing destination. Filesystems without hard-link support fail closed. Temporary files can remain after an uncatchable termination or power failure and should be removed manually.

## Deterministic interoperability vector

Parameters:

```text
master key hex:
000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f

file salt hex:    000102030405060708090a0b0c0d0e0f
nonce prefix hex: 1011121314151617
chunk size:       4096
plaintext ASCII:  GEM
```

The complete 115-byte container in Base64 is:

```text
R0VNU0VBTDEBAAEAAQAwAAABAgMEBQYHCAkKCwwNDg8QERITFBUWFwAQAAAAAAAAAQABABMAAAAAAAMAAAAAAP3eBxRxm6eRP8nLh/BwOe63868CAAEAEAABAAAAAAAAAAAAQSBHysL8RkaySCG8VwtLCA==
```

A compatible decoder using the stated master key must produce exactly three plaintext bytes, `GEM`, and accept no trailing bytes. This vector covers HKDF, one DATA record, previous-tag chaining into END, and empty END plaintext.

## Compatibility policy

A decoder must not guess at unknown versions or suite identifiers. Changes to field encoding, KDF context, AAD context, nonce construction, or record semantics require a new format version or suite identifier. The atomic-publication behavior is an implementation property and does not alter version 1 ciphertext.
