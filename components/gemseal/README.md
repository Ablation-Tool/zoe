# GEMSEAL

GEMSEAL is a GEM-inspired authenticated-encryption file container and reference implementation. It combines structural ideas from Digital Research's Graphics Environment Manager with HKDF-SHA256 and ChaCha20-Poly1305.

**This is an experimental, independently unaudited format, not a native GEM cipher and not a replacement for an audited tool such as `age`.** AES in the GEM manuals means Application Environment Services, not Advanced Encryption Standard.

## What it provides

- Raw 32-byte master keys generated by the operating system CSPRNG.
- A different HKDF-SHA256 file key for each random file salt.
- Streamed ChaCha20-Poly1305 encryption with unique per-record nonces.
- Authentication of the file header, record order, record contents, and preceding tag.
- Detection of wrong keys, modification, reordering, truncation, and trailing data.
- Streaming without a GEM resource file's historical 64 KiB limit.
- Temporary-file output and atomic, no-overwrite publication only after complete success.

The visual relationships are design motifs only. GEM raster XOR, AES messages, and RSC resources provide no cryptographic security themselves.

## Requirements and installation

- Python 3.8 or newer.
- `cryptography` 41 or newer.
- A filesystem that supports hard links for atomic publication.

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install .
```

Use a native filesystem with working permission enforcement for keys and decrypted files. The program requests owner-only (`0600`) temporary and output files, but some mounted filesystems override those permissions.

## Quick start

```sh
gemseal keygen key.bin
gemseal encrypt key.bin document.pdf document.pdf.gemseal
gemseal decrypt key.bin document.pdf.gemseal document.restored.pdf
```

The destination must not already exist. Keep `key.bin` separate from encrypted files and protect it from disclosure and loss. There is no key-recovery mechanism.

Without installing, run the same commands as:

```sh
python3 gemseal.py keygen key.bin
python3 gemseal.py encrypt key.bin document.pdf document.pdf.gemseal
python3 gemseal.py decrypt key.bin document.pdf.gemseal document.restored.pdf
```

An optional `--chunk-size` changes the encryption chunk size from its 4096-byte default. The maximum is 65519 bytes. Decryption reads the value from the authenticated file header.

## Visual guide

The following example encrypts a 10,000-byte file using the default chunk size.

### 1. Key and nonce generation

```text
                    Operating-system cryptographic RNG
                    /                              \
           16-byte random salt              8-byte nonce prefix
                   |                                |
32-byte master key |                                |
        \          |                                |
         HKDF-SHA256                                |
              |                                     |
       Unique file key                              |
              |                                     |
              +------------------+------------------+
                                 |
                    For each record number i:
                                 |
                 nonce = nonce_prefix || LE32(i)
                                 |
                       12-byte unique nonce
```

The random salt produces a different file key even when one master key encrypts multiple files. The counter makes each nonce within one file key unique.

### 2. Plaintext becomes GEM-style records

```text
Plaintext: 10,000 bytes

                  Split into chunks
                           |
          +----------------+----------------+-----------+
          |                |                |           |
       4096 bytes       4096 bytes       1808 bytes    Empty
          |                |                |           |
       Record 0         Record 1         Record 2     END record
```

Each record has a GEM-message-inspired 16-byte header:

```text
Byte offset:
 0       2       4       6               10              14       16
 |-------|-------|-------|---------------|---------------|--------|
 | Type  | Suite | Sealed| Record index  | Plaintext     | Flags  |
 |       |       | length|   uint32      | length uint32 |        |
 | 2 B   | 2 B   | 2 B   |     4 B       |     4 B       |  2 B   |
 |-------|-------|-------|---------------|---------------|--------|

Type: DATA or END
Sealed length: ciphertext bytes plus the 16-byte authentication tag
```

GEM's word 2 counts bytes beyond its predefined 16-byte message. GEMSEAL uses the same structural idea for the sealed body length, but these records are not GEM AES messages.

### 3. Inside each encrypted record

```text
                         File key + unique nonce
                                  |
                                  v
Plaintext chunk --------> ChaCha20 encryption --------> Ciphertext
                           (XOR keystream)
                                                               |
                                                               v
Additional authenticated data ---------> Poly1305 --------> 16-byte TAG
(AAD)                                      ^
                                           |
                                    AAD + ciphertext
```

This is a simplified AEAD diagram. The precise inputs are:

```text
AAD for record i
   =
"GEMSEAL1/record\0"
+ complete 48-byte file header
+ previous record's TAG
+ current 16-byte record header
```

For the first record, the previous tag is sixteen zero bytes. The XOR operation uses ChaCha20's cryptographic keystream, not GEM raster XOR or Dungeon's position-based XOR routine.

### 4. Final encrypted file

```text
+----------------+-----------------------------------------------------+
| 48-byte header |                 Encrypted records                   |
+----------------+-----------------------------------------------------+
        |
        v
+----------+------------+----------+------------+----------+------------+
| Record 0 | C0 + TAG0  | Record 1 | C1 + TAG1  | Record 2 | C2 + TAG2  |
| header   |            | header   |            | header   |            |
+----------+------------+----------+------------+----------+------------+
                                      |
                                      v
                            +---------+---------+
                            | END header + TAG3 |
                            +-------------------+
```

The tags form an authentication chain:

```text
TAG0 --included in AAD--> Record 1
TAG1 --included in AAD--> Record 2
TAG2 --included in AAD--> END record
```

Changing, removing, or reordering a record breaks this chain. The END record authenticates completion and prevents accepting a merely truncated prefix as a valid file.

### 5. Decryption and publication

```text
Read file header
       |
Derive file key with HKDF-SHA256
       |
       +---------------- For each record ----------------+
       |                                                  |
       v                                                  |
Reconstruct nonce and AAD                                 |
       |                                                  |
Verify Poly1305 TAG                                       |
       |                                                  |
       +---- Invalid --> Stop and remove temporary output |
       |                                                  |
     Valid                                                |
       |                                                  |
ChaCha20 decrypt                                          |
       |                                                  |
Write to temporary file (0600 requested)                 |
       |                                                  |
       +--------------------------------------------------+
       |
Authenticated END record found and no trailing bytes?
       |
       +---- No  --> Remove temporary output
       |
      Yes
       |
Atomically publish without overwriting an existing path
       |
Decryption successful
```

The destination pathname is not created while records are still being verified. This avoids exposing partial plaintext at the final pathname after a late authentication failure.

## Testing and strength assessment

Run the standard-library test suite from the repository root:

```sh
python3 -m unittest discover -s tests -v
```

The tests cover normal and empty files, exact chunk boundaries, randomized containers, the deterministic vector, wrong keys, tampering, truncation, reordering, trailing data, atomic publication, interruption cleanup, PIN and wordlist recovery, reduced raw-key searches, and candidate limits.

### Weak-key demonstration

The following deliberately uses `SHA256("0420")` as a master key. This is not how `gemseal keygen` generates keys; it demonstrates what happens when a user substitutes a predictable key-derivation scheme.

```sh
python3 - <<'PY'
import hashlib
from pathlib import Path
Path("weak-key.bin").write_bytes(hashlib.sha256(b"0420").digest())
Path("message.txt").write_text("Attack at dawn\n")
PY

gemseal encrypt weak-key.bin message.txt weak.gemseal
gemseal-crack pin weak.gemseal --digits 4 --output recovered.txt
```

The attack searches `0000` through `9999`, reports candidates per second, recovers `0420`, and fully decrypts the container. Delete the demonstration key when finished.

Test a binary wordlist (one candidate per line) with:

```sh
gemseal-crack wordlist weak.gemseal candidates.txt --mode sha256 --output recovered.txt
```

Candidate transforms are:

- `sha256`: SHA-256 of each candidate byte string; useful for demonstrating unsafe home-grown password handling.
- `zero-padded`: candidate bytes padded on the right with zero bytes to 32 bytes.
- `raw`: candidate must already contain exactly 32 bytes.

For a deliberately reduced raw-key space, vary only the first one to four bytes and set all remaining key bytes to zero:

```sh
gemseal-crack raw-prefix reduced.gemseal --variable-bytes 2
```

Use `--limit N` to bound an experiment. `--output` performs full-container verification and atomic decryption after first-record recovery. Without it, the tool only reports that the first authentication tag matched. Exit statuses are 0 for recovered, 1 for not found, 2 for an error, and 130 for interruption. Use the cracker only on your own containers or with explicit authorization.

### How to interpret the results

- The authentication tag gives an attacker an offline candidate check: derive a candidate file key and test the first record. No server or rate limiter is involved.
- A four-digit PIN has only 10,000 possibilities and should be recovered quickly. A fast SHA-256 transform does not add password stretching.
- Measured candidates-per-second rates are useful for dictionary and reduced-space estimates on the same machine. They are not a universal cracking speed.
- A short search that fails against a `gemseal keygen` key proves almost nothing. Exhaustively searching a random 256-bit key is computationally infeasible; demonstrating a small sample of failures is not a security proof.
- Round trips and corruption tests establish functional behavior, not cryptographic security. Independent cryptanalysis and implementation review are still required.

## AI and vault access tripwire

`gemseal-tripwire` adds a thin **detection layer** for encrypted files. It does not prevent access or hide the vault; it records access attempts so they can be correlated with AI, agent, shell, and system logs.

```text
AI or user opens an encrypted vault file
                    |
                    v
          Linux inotify watcher
                    |
          +---------+---------+
          |                   |
     JSON audit event    Immediate alert
     outside vault       on stderr
```

Create a demonstration vault with an encrypted canary and its key outside the watched directory:

```sh
gemseal-tripwire init /safe/vault /safe/private/vault.key
gemseal-tripwire watch /safe/vault --log /safe/audit/vault.jsonl
```

In another terminal, opening the canary should produce `open` and possibly `read` events:

```sh
head -c 16 /safe/vault/project_notes.gemseal
```

Add real encrypted files with the existing command:

```sh
gemseal encrypt /safe/private/vault.key secret.pdf /safe/vault/secret.pdf.gemseal
```

Use `--once` for a single-event test and `--dedup 0` for verbose events. The watcher must be running before access occurs. It records paths and event types, not the accessing PID or user. It also cannot stop reads, guarantee detection of directory enumeration, or protect logs from an AI running with equivalent privileges.

See [the tripwire guide](docs/TRIPWIRE.md) for deployment, JSON examples, process attribution options, and the complete threat model. For an agent-attack investigation workflow, see the [formal Cerotto forensic integration plan](docs/CEROTTO_FORENSIC_PLAN.md).

## Security boundary

GEMSEAL is designed to protect file contents against an attacker who has the ciphertext but not the random master key, and to detect ciphertext modification. It does not provide:

- Password-based encryption or password stretching.
- Sender signatures, non-repudiation, or forward secrecy.
- Filename, file-size, record-count, or timing confidentiality.
- Protection against endpoint compromise, key theft, or memory inspection.
- Guaranteed removal of keys/plaintext from Python memory or storage media.
- Guaranteed cleanup of temporary files after `SIGKILL` or power loss.
- Interoperability with GEM AES messages, RSC resources, or GEM metafiles.

See [the format specification](docs/FORMAT.md) for exact bytes and a deterministic vector, and [the review](docs/REVIEW.md) for book coverage, corrected flaws, remaining limitations, and verification status.
